# Scientific AI Evaluation Notes

This project is not an AI model or LLM benchmark. Its value for scientific AI
conversations is that it demonstrates habits needed when evaluating AI systems
on technical domains: explicit assumptions, reproducible examples, numerical
checks, visual inspection, and clear limits on what the output means.

## Evaluation Habits Demonstrated

### Separate Model, Data, And Claims

The README distinguishes between:

- governing equations,
- browser-side implementation,
- synthetic built-in overlays,
- user-imported CSV data,
- calibration of prescribed spreading parameters,
- exploratory reports,
- validation caveats.

This separation is directly relevant to AI evaluation work where prompts,
tools, datasets, expected answers, and unsupported claims must not be mixed.

### Preserve Physical Constraints

The app keeps normalized variables and model boundaries visible. That supports
questions such as:

- Does a generated explanation respect the variables and units?
- Does a generated analysis confuse synthetic examples with validation data?
- Does a model report overstate a numerical fit as physical validation?
- Does a proposed workflow preserve caveats during export or summarization?

### Use Multimodal Evidence

The project combines text, equations, plots, 3D geometry, CSV output, and
browser-side reports. This makes it a useful public example for evaluating how
AI systems handle technical tasks that mix language, visual interpretation, and
structured numerical data.

### Keep Failure Modes Visible

The app intentionally states what it does not compute. This is a strength for
scientific AI evaluation because it gives reviewers clear failure categories:

- treating synthetic data as measured data,
- treating exploratory fitting as validation,
- treating setup aids as solver-ready CFD,
- treating a reduced-order model as full transient spray physics,
- omitting uncertainty and applicability limits.

## Possible Future Mini-Eval

A safe public mini-eval could use only synthetic examples generated by this app.
Tasks could ask a model to:

1. Identify variables and units from an exported CSV.
2. Summarize one plot without claiming physical validation.
3. Explain why a parameter fit is not a validated engineering result.
4. Translate a short technical caveat between English, Japanese, and Spanish.
5. Flag an intentionally overclaimed report sentence.

This would be an evaluation of technical reasoning and caveat preservation, not
a benchmark of frontier model performance.
